#### 常用的散列表数据结构
`HashMap`、`HashTable`、`ConcurrentHashMap`

#### HashMap 和 HashTable 的对比

##### 相同点
- 数据结构：都使用哈希表 + 链表的方式。
- `fail-fast`：都具有 `fail-fast` 机制。

##### 不同点
- 实现方式：`HashTable` 继承了 `Dictionary` 类，而 `HashMap` 继承的是 `AbstractMap` 类。
- 初始化容量：`HashMap` 的初始容量是 `16`，而 `HashTable` 的初始容量是 `11`，两者的负载因子都默认是 `0.75`。
- 扩容机制：当现有容量大于总容量 * 负载因子时，`HashMap` 扩容规则为当前容量翻倍，`HashTable` 扩容规则为当前容量翻倍 + 1。
- 线程安全性：`HashTable` 是线程安全的，`HashMap` 是线程不安全的。
- 效率：`HashMap` 的效率要高于 `HashTable`。

#### HashMap 和 ConcurrentHashMap 对比

##### 相同点
- 数据结构：都使用哈希表 + 链表的方式。
- 实现方式：两者都继承了 `AbstractMap` 类。

##### 不同点
- 线程安全性：`ConcurrentHashMap` 是线程安全的，`HashMap` 是线程不安全的。
- 红黑树结构：`HashMap` 的红黑树中的节点叫做 `TreeNode`，`TreeNode` 不仅仅有属性，还维护着红黑树的结构，比如说查找，新增等等；`ConcurrentHashMap` 中红黑树被拆分成两块，`TreeNode` 仅仅维护的属性和查找功能，新增了 `TreeBin`，来维护红黑树结构，并负责根节点的加锁和解锁。
- `fail-fast`：`HashMap` 具有 `fail-fast` 机制，`ConcurrentHashMap` 不具备 `fail-fast` 机制。
 
#### HashTable 是如何做到线程安全的
`HashTable` 通过使用大量 `synchorinzed` 关键字来保证线程安全。

#### ConcurrentHashMap 是如何做到线程安全性的
在 `Java 1.8` 之后 `ConcurrentHashMap` 在 `put` 键值对时通过 `CAS + Sycnhorinzed` 的方式保证线程安全。具体流程如下：

1. 通过计算如果 `key` 所对应哈希数组的位置上没有数据，则通过 `CAS` 的方式为为此位置赋值。
2. 如果位置上有值，则通过 `synchorinzed` 加锁保证当前仅有一个线程可以操作链表或红黑树。

#### 为什么 ConcurrentHashMap 的读取方法不需要加锁
这是因为 `ConcurrentHashMap` 中哈希表、数组元素、链表节点、数节点都使用了 `volatile` 修饰。`volatile` 可以保证数据的可见性和有序性，但不保证原子性。

#### 为什么 ConcurrentHashMap 不需要 fail-fast 机制
- `fail-fast`：是指在遍历过程中，如果数据结构发生变化，就抛出异常停止遍历。
- 原理：通过判断 `modCount` 的值判断是否数据结构发生了变化，当数据发生变化时 `modCount` 自加1，当遍历数据前赋值 `expectedModCount = modCount`，在遍历过程中如果 `if (modCount != expectedModCount)` 则抛出异常。
- 目的：防止在并发情况下，数据发生变化

为什么 `ConcurrentHashMap` 不需要 `fail-fast` 机制：因为 `volatile` 关键字的存在，让 `ConcurrentHashMap` 不用担心并发状态下的数据修改。

#### 数组下标计算
`HashTable` 使用取余的方式计算对应数组下标：
```
int index = (hash & 0x7FFFFFFF) % tab.length;
```

`HashMap` 和 `ConcurrentHashMap` 通过按位与 `&` 计算：
```
i = (n - 1) & hash
```
首先按位运算效率更高，并且通过 `&` 可以保证计算结果 `<n`

```
假设 n = 16，hash = 100

所以 i = 15 & 100

`&` 计算：
0001111
1100100
结果：
0000100
```
但是通过数组长度参与 `&` 运算会导致仅有 `hash` 低位的值参与运算，导致计算结果冲突的概率增加，所以 `HashMap` 和 `ConcurrentHashMap` 都通过 `hash` 高位和低位进行 `^` 的方式让 `hash` 高位参与了运算：

```
(h ^ (h >>> 16)) & HASH_BITS
```

这样可以减少冲突的产生。其中 `HASH_BITS` 的值是 `0x7fffffff` 转换为二进制是 `01111111111111111111111111111111` 这个操作后会把最高位转为 0，其实就是消除了符号位，得到的都是正数。
> 其实 `& HASH_BITS` 操作并不理解它的含义。因为就算 `^` 运算结果为负值，和 `(n-1)` 进行 `&` 运算后得到的结果也必定是正值。

#### 为什么 HashMap 的数组大小必须是 2 的 n 次方
因为 `HashMap` 和 `ConcurrentHashMap` 是通过位运算计算对应数组下标的，所以当数组大小为 `2` 的 `n` 次方时可以减少计算得到数组下标的碰撞几率。

`ConcurrentHashMap` 计算 `key` 对应数组下标的方式如下：

```
i = (n - 1) & hash
```

如果 `hash` 值的二进制是 10000（十进制16）、10010（十进制18）、10001（十进制17），和10100做&计算后，都是10000，也就是都被映射到数组16这个下标上。这三个值会以链表的形式存储在数组16下标的位置。这显然不是我们想要的结果。
但如果数组长度n为2的n次方，2进制的数值为10，100，1000，10000……n-1后对应二进制为1，11，111，1111……这样和 `hash` 值低位&后，会保留原来 `hash` 值的低位数值，那么只要hash值的低位不一样，就不会发生碰撞。

同时 `(n - 1) & hash` 等价于 `hash%n` 。那么为什么不直接用 `hash%n` 呢？

这是因为按位操作效率更高，这也是在单线程情况下 `HashMap` 效率高于 `HashTable` 的原因。

#### 扩容逻辑

#### 为什么链表转化为红黑树选择 8 为节点
首先链表时间复杂度 `O(n)` 要低于红黑树的时间复杂度 `O(logn)`，但是红黑树节点占用的空间要大于链表。根据时间和空间平衡的思想，最开始使用链表的时候，空间占用是比较少的，而且由于链表短，所以查询时间也没有太大的问题。可是当链表越来越长，需要用红黑树的形式来保证查询的效率。
至于为什么选择 `8` 作为转换节点这是因为在理想状况下，链表长度要达到 `8` 几率是非常低的，大概是千万分之一的概率，所以通常情况下不会发生链表转换为红黑树的情况。
但是，`HashMap` 决定某个值放到哪个节点是跟 `HashMap` 相关的，如果开发者重写了 `hashCode` 函数导致哈希算法变的不均匀，那就有可能导致 `HashMap` 中某个节点的链表非常长，链表长度超过 8 就转为红黑树的设计，更多的是为了防止用户自己实现了不好的哈希算法时导致链表过长，从而导致查询效率低，而此时转为红黑树更多的是一种保底策略，用来保证极端情况下查询的效率。

#### 为什么使用头插法
一、先看什么是头插法

JDk7 通过 hashcode&（Length-1）后的一系列异或运算计算出数组的 index：

1).如果这个 index 位没有元素则直接占位；

2).只有一个元素时，开始比较 key 是否是同一个对象，如果是同一对象则覆盖，否则把当前 entry.next 指向原来 entry，让其退位让贤，称为头插；

3).问题来了，当这个位置有 n 个 entry 时，则要遍历出每个 entry，然后去比较当前 key 与遍历出来的是否是同一个 key，是则接覆盖并退出循环，否则进行下一次遍历，都没有同样的 key 会遍历完整个 entry 链。既然都要遍历完整个 entry，为什么不直接在尾部插入呢，用尾插法不行么？

其实很简单，头插法大多数情况是方便第一和第二种情况的，因为散列性好的话 hash 冲突的概率自然比较小，没有元素或只有一个元素，遍历个锤子，减少遍厉次数呗。而且既然第一和第二种情况时已经写了一个头插方法，就没必要再写一个尾插方法了吧。

二、Jdk8 使用尾插法，为什么呢。

1).因为 jdk8 里的单向链表变成红黑树时的条件是确定的，node 链长度+1 大于等于 8 且容量大于 64 时扩容，遍历几次而已，那就可以放心遍历啦，于是就用了尾插法，为了写代码方便。

2).头插法在并发扩容时，会形成死环，但我觉得这并不是改成尾插法的主要原因，因为在并发情况使用 hashmap 本身是错误的用法。

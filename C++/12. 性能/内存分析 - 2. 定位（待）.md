要做到“函数级别定位”，必须结合**内存分析工具或采样器**。常见方法：

### 🔍 方式 A：`malloc`/`free` 拦截（用户态追踪）

* 使用 `LD_PRELOAD` 动态库，重载 `malloc/free` 等函数，打印调用栈
* 工具：`libasan`、`jemalloc` 的 prof、`tcmalloc` 的 heap profiler、`malloc_logger`
* 可以看到 **哪个函数调用 `malloc`，大小多少**

👉 优点：函数精确，能定位泄漏点
👉 缺点：有开销，可能影响性能

---

### 🔍 方式 B：采样分析（低开销，线上常用）

* **perf** + `malloc` 事件采样

  ```bash
  sudo perf record -e malloc:malloc -aR sleep 10
  sudo perf report
  ```

  可以采样 malloc 调用点，结合符号表得到调用栈
* **heaptrack** (Linux 上常用)

  ```
  heaptrack ./your_program
  heaptrack_gui heaptrack.your_program.XXXX.gz
  ```

  可以生成调用图，显示哪个函数分配了多少内存

👉 优点：可视化强，适合诊断
👉 缺点：需要带调试符号，文件可能较大

---

### 🔍 方式 C：编译时插桩 / 动态追踪

* **AddressSanitizer (ASan)**：能发现越界/泄漏，但对内存使用较重
* **Valgrind / Memcheck**：非常精确，但慢（适合离线复现）
* **bcc/eBPF** 工具：比如 `memleak`（内核级追踪 malloc/free，堆栈回溯）

---

## 3️⃣ 栈溢出类问题

如果是 **栈溢出**：

* 崩溃时 core dump 里能看到调用栈，直接显示最后的函数
* 或用 `ulimit -c unlimited` + `gdb core` 分析

---

## 4️⃣ 线程泄漏类问题

如果是 **线程泄漏**：

* 在 `maps` 里会出现大量 `[stack:<tid>]`
* 用 `pstack <pid>` 可以打印所有线程栈，直接看到函数卡在哪

---

## ✅ 总结

* **maps/smaps → 只能看到内存段**，不能定位函数
* **要到函数级别**，需要：

  * 动态追踪（perf, heaptrack, eBPF）
  * 内存替换器（jemalloc profiler, tcmalloc profiler）
  * 调试器/Valgrind（更重型）

---

📌 实际建议：

* **线上监控**：先用 `top + maps/smaps` 发现问题（轻量）
* **定位函数**：用 `heaptrack` 或 `perf + debug symbols`，分析哪个函数分配最多
* **开发/测试时**：用 `ASan/Valgrind` 精确查泄漏

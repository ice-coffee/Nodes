### 定义

**全局符号表** 是一个由编译器、汇编器或链接器创建和维护的数据结构（通常是一个哈希表或字典），它存储了在一个程序的所有目标文件或编译单元中定义和引用的**全局符号** 的信息。

*   **符号**： 指的是一个变量或函数的名称。
*   **全局**： 指的是这个符号的可见性跨越了单个源文件的边界，可以被整个程序的其他部分看到和访问。

简单来说，全局符号表就是整个程序的“通讯录”或“索引”，记录了所有“公共”的变量和函数的名字以及它们的详细信息，以便在链接阶段能够正确地将它们关联起来。

### 全局符号表中包含哪些信息？

对于一个符号（例如一个全局变量 `int global_var;` 或一个函数 `void my_func(){}`），符号表通常会记录以下信息：

1.  **符号名**： 变量或函数的名称（例如 `global_var`, `my_func`）。
2.  **符号类型**：
    *   **对于变量**： 类型信息（如 `int`, `double`, `struct MyStruct` 等）。
    *   **对于函数**： 返回类型和参数类型（即函数签名）。
3.  **存储类别**： 表明是全局变量、静态变量、外部变量等。
4.  **作用域和链接性**： 表明这个符号是全局的（`global`）还是局部的（`local`，如 `static` 变量），以及它的链接是外部的（`external`）还是内部的（`internal`）。
5.  **大小**： 变量或函数所占用的内存大小（字节数）。
6.  **地址/偏移量**： 这是最关键的信息之一。
    *   在**目标文件**中，它可能是该符号在某个段（如 `.data`, `.text`）中的偏移量。
    *   在**可执行文件**中，它最终会被解析为虚拟内存地址（Virtual Address）。

### 全局符号表的主要作用

它的存在主要是为了服务**链接器**，解决“拼图”问题。

1.  **符号解析**：
    *   当你在一个源文件 `a.c` 中使用了在另一个源文件 `b.c` 中定义的全局变量或函数时，编译器在编译 `a.c` 时并不知道这个符号在哪里，它只会做一个**符号引用**，并把这个未解决的引用记录在目标文件 `a.o` 的符号表中。
    *   链接器会收集所有目标文件（`a.o`, `b.o`, ...）的符号表，合并成一个全局视图。
    *   链接器的工作就是为每一个**符号引用**找到对应的**符号定义**。如果找不到，就会报“未定义的引用”错误；如果找到多个同名的全局定义，就会报“重复定义”错误。

2.  **重定位**：
    *   编译器在生成目标文件时，通常假设代码从地址 `0` 开始。但显然，多个目标文件最终需要被合并到一个地址空间中，它们的代码和数据会被分配到不同的地址。
    *   链接器确定了每个符号在最终内存映像中的实际地址后，会去修改所有引用该符号的指令（例如跳转指令 `call my_func` 的地址需要被修正为 `my_func` 的真实地址）。这个过程就是**重定位**，而全局符号表提供了重定位所需的地址信息。


#### 1. 哪些符号会进入全局符号表

运行时的 **全局符号表**（由动态链接器维护）并不是 ELF 文件里的 `.symtab`，而是进程级的“可见符号集合”。

进入条件主要有：

1. **绑定属性是 GLOBAL** 的导出符号（见 `readelf -s` → `Bind` 字段）。

   * `LOCAL` 的符号永远不会导出。
   * `GLOBAL` + `DEFAULT` visibility 的才可能被导出。
   * `HIDDEN/PROTECTED` visibility 的，即便是 GLOBAL 也不会进入全局表。

2. **由主程序或以 `RTLD_GLOBAL` 加载的库导入**。

   * 主程序（可执行文件）默认把自己的符号都放进全局表。
   * `dlopen(..., RTLD_GLOBAL)` 的库会把它的导出符号放进全局表。
   * `dlopen(..., RTLD_LOCAL)` 的库不会影响全局表，它的符号仅对自己和依赖库可见。

3. **静态库符号的情况**

   * 如果静态库（`.a`）直接被打包进 `.so`，那么符号默认就是 `GLOBAL`，除非用 `-fvisibility=hidden` 或 `--exclude-libs` 隐藏。

---

#### 2. 存在相同符号时会如何处理

动态链接器遵循 **第一次定义优先** 的原则：

* 当库 A 的符号 `foo` 已经放入全局符号表，
* 后加载的库 B 里也有同名 `foo`，
* **不会覆盖**，库 B 内部如果需要 `foo`，它会用全局表里的 A::foo。

这样会导致几个后果：

* 如果 A 和 B 是不同版本的库（比如两份 protobuf），就会产生 **符号劫持** —— B 里本想用自己版本的 `foo`，结果用的是 A 的 → ABI 不兼容 → 崩溃。
* 如果 B 内部强依赖自己的实现，可以通过 `-Bsymbolic` 或 `RTLD_DEEPBIND` 避免全局解析，但这会破坏一致性，容易引发 bug。

#### 3. 库加载顺序对全局符号表的影响

符号表是 **随着库加载顺序逐步填充** 的，所以顺序至关重要。

1. **主程序先行**

   * 可执行文件里的符号最先进入全局表。
   * 所以即使动态库有相同符号，也不会覆盖。

2. **依赖库的加载顺序**

   * `dlopen`/`ld.so` 会根据依赖顺序依次加载库，先加载的库符号会先进入全局表。
   * 后加载的库如果有相同符号，解析时会命中前面的定义。

3. **LD\_PRELOAD**

   * 如果通过 `LD_PRELOAD` 预先加载库，那么它的符号最早进入全局表，相当于“抢占”了解析权。
   * 这就是常见的 hook 技术。

4. **RTLD\_LOCAL vs RTLD\_GLOBAL**

   * `RTLD_LOCAL`：符号仅本库可见，不影响全局表。
   * `RTLD_GLOBAL`：符号导出到全局表，可能影响后续库的解析。

### 一个简单的例子

假设我们有两个文件：

**main.c**
```c
extern int global_var; // 声明一个外部全局变量
void hello();          // 声明一个外部函数

int main() {
    global_var = 10;
    hello();
    return 0;
}
```

**utils.c**
```c
#include <stdio.h>
int global_var; // 定义全局变量

void hello() {  // 定义函数
    printf("Hello, value is %d\n", global_var);
}
```

**编译和链接过程：**

1.  **编译 `main.c` 成 `main.o`**：
    *   编译器遇到 `global_var` 和 `hello`，但找不到它们的定义。
    *   它会在 `main.o` 的符号表中创建两个**未定义的引用**（`UND`），标记为 `extern`，表示需要从外部寻找。

2.  **编译 `utils.c` 成 `utils.o`**：
    *   编译器找到了 `global_var` 和 `hello` 的定义。
    *   它会在 `utils.o` 的符号表中创建两个**已定义的符号**，并记录它们在 `.data` 段和 `.text` 段中的位置。

3.  **链接器工作**：
    *   链接器读取 `main.o` 和 `utils.o` 的符号表，生成一个全局符号表。
    *   它在全局符号表中查找 `main.o` 引用的 `global_var` 和 `hello`，并在 `utils.o` 中找到了它们的定义。
    *   链接器将两个目标文件的数据段和代码段合并，并为所有段和符号分配最终的内存地址。
    *   链接器根据全局符号表中的地址信息，回到 `main.o` 的代码中，将 `call hello` 这条指令的地址修改为 `hello` 函数的真实地址。同样，对 `global_var` 的访问地址也会被修正。

4.  **输出可执行文件**： 最终生成的可执行文件中包含了一个完整的、地址已修正的全局符号表（虽然通常会被剥离以减小文件大小，但调试信息中会保留）。

### 如何查看全局符号表

#### 1. 静态分析

* `nm -D libxxx.so` 可以列出动态库导出的符号（即可能进入全局表的符号）。
* `readelf -s libxxx.so` 也能查看符号表，能看到绑定类型（`GLOBAL` / `LOCAL`）。

#### 2.运行时

* `ldd ./your_app` 查看运行时加载了哪些库。
* `LD_DEBUG=bindings ./your_app` 可以打印符号解析的过程，看到某个符号从哪个库解析。
* `cat /proc/<pid>/maps` 查看进程加载的所有库地址。

### 符号查找顺序

通常符号解析时，顺序如下：

1. **主程序（可执行文件）** 的符号先被加入全局表，优先级最高。
2. 使用 `dlopen(..., RTLD_GLOBAL)` 加载的库，其符号会被放进全局表。
3. 普通 `dlopen(..., RTLD_LOCAL)` 的库，符号不会影响全局表，只能在自己依赖的库里查找。

因此，不同加载顺序、`RTLD_GLOBAL`/`LOCAL` 的选择，会直接决定是否产生“多份 runtime”的问题（比如你之前问的 protobuf 符号冲突）。

### 常用解决办法

* **隔离符号**

  * 链接时加 `-Wl,--exclude-libs,ALL`，避免静态库符号被导出。
  * 使用 `-Wl,--version-script` 或 `__attribute__((visibility("hidden")))` 控制导出符号。
* **指定加载顺序**

  * 用 `LD_PRELOAD` 预先加载需要的库，确保它的符号进全局表。
* **避免冲突库**

  * 确保进程只加载一份相同依赖库（比如 protobuf）。

### 架构
架构存在的意义：解耦。

什么是架构：架构就是模块与模块之间，层与层之间解耦的一种编程思想。

架构需要满足的条件：

- `框架独立`：架构不依赖于一些满载功能的软件库。
- `可测试性`。
- `视图层独立`：在不改变系统其余部分的情况下完成对UI的简易更改。
- `数据层独立`：业务规则不绑定与某个具体的数据库当中，可以随意更换数据库的具体实现：比如说从SQL切换到BigTable,这种情况不会对务规则产生影响。
- `业务逻辑间彼此独立`：业务规则完全不知道外层的事情。

#### 常见架构
在 [architecture-samples](https://github.com/android/architecture-samples) 中展示了使用不同架构开发 `Android` 项目。

##### MVC
M：数据层，负责处理本地及线上数据。
V：视图层，负责更新视图。
C：业务逻辑层，连接 `M`、`V`，并实现具体业务逻辑。 

核心：分离业务逻辑。

优点：

- 将数据层、视图层、业务逻辑层代码分离。代码清晰。

缺点：

- 数据层、视图层耦合。
- 逻辑层不易测试。
- 数据层代码承担了一部分逻辑代码的实现。

##### MVP
使用 `MVP` 模式可以弥补 `MVC` 模式中数据层、视图层耦合且逻辑层不易测试的问题。`MVP` 中以 `P` 层代替了 `MVC` 模式中的 `C` 层。它们其实都是业务逻辑层。区别是 `P` 层完全承接了数据层和视图层的通信任务，使这两层之间分离的更加彻底。

核心：在分离业务逻辑的基础上，解耦视图层和数据层。

优点：

- 数据层、视图层完全分离解耦。
- 易于测试业务逻辑。

缺点：

- 需要定义大量接口
- 当有业务变动时需要对大量代码进行修改。比如业务变动时需要修改接口导致接口调用和接口实现也要做相应调整。
- 依然需要在数据层中实现部分逻辑代码。

##### MVVM
M：数据层，负责处理本地及线上数据。
V：视图层，负责更新视图。
VM：视图模型层，为视图层提供数据模型，并调用数据层更新数据模型实现具体业务逻辑。 

通过 `MVVM` 可以省去 `MVP` 架构定义的大量接口以 `DataBinding` 等手段更新视图层。`MVVM` 架构中使用 `Jetpack - LiveData、ViewModel` 可以编写出更加优秀的项目。

核心：在 `MVP` 的基础上，实现数据监听以及数据绑定代码结构更简洁。

优点：

- 数据层、视图层完全分离解耦。
- 易于测试业务逻辑。
- 不需要定义大量接口通过数据监听和数据绑定更新视图并响应视图层事件实现业务逻辑。
- 视图层中不需要添加额外逻辑代码。

缺点：

- 学习成本高。需要熟练使用 `LiveData`、`ViewModel`、`DataBinding` 等库。
- 由于目前 `IDEA` 对 `DataBinding` 的支持问题，代码提示、BUG 定位都是比较棘手的问题。

> `注意`：在 `MAX` 架构中，`M` 被很多人拿理解为数据实体，这种理解其实是错误的，它指代的是模块中负责对数据进行加载、缓存等操作的整体层级。出现这种理解大概率是在一些小公司的项目中可能因为业务逻辑简单导致 `P` 仅发挥其连接 `M、V` 两层的通道的作用，且项目中没有添加类似数据库等对数据进行缓存等处理的设计导致 `M` 层仅剩数据实体，所以才会有这样的感觉。
> `再次注意`：没有绝对正确的架构，只有最合适的架构。如果项目逻辑确实过于简答，那么对 `MVX` 架构进行调整和删减也是可以的。

#### Repository 模式
`Repository` 模式将 `MVX` 模式中 `M` 对于数据处理的部分抽离整合使其仅剩数据模型的功能，对于数据处理由 `Repository` 统一处理。所以有无 `Repository` 模式的 `MVX` 架构 `M` 层的职责是不一样的。

### 模块化
将应用程序按业务拆分，形成独立的模块 `module`，也就是 `Android Studio` 提供的 `module`。每个模块只包含其业务相关的内容。例如：登录模块、首页模块、购物车模块、物流模块等。

- 功能模块
    - HTTP
    - Glide
    - EventBus
    - Router
    - Utils
    - 等等
- 业务模块
    - 相关业务或流程的集合
        - 数据层
        - 视图层

如果一个项目按照模块划分基本都可以划分为 `功能模块`、`业务模块` 两个模块。

对于功能模块来说，市面上有大量优秀的开源项目供你选择。比如网络库 `Volley`、`OkHttp`、`Retrofit`；图片库 `Glide`、`Picao`、`kotlin-first`；作为开发者需要做的就是根据业务场景和现实情况进行选择并做好随时被替换的准备。

对于业务模块来说，一系列可单独存在的相关操作的集合为一个业务模块，比如登录注册、商城购物车、聊天等。开发者需要将各个业务模块独立分割，使之互不影响。业务模块细分又分为 `数据层`、`视图层`：
`数据层`：与数据源（本地数据、后端服务数据）交互。比如本地数据库的增删改查、接口访问等。
`视图层`：与用户交互。相应用户手势及点击等事件。

对于视图层来说应该保证操作的单一性。对于用户可能触发的任何操作以及其可能引发的连锁反应单独处理。
对于数据层来说就是为视图层提供内容数据，供视图层展示。

Data Mapper：将 `数据层`、`视图层` 解耦分离，防止 `数据层` 中事先定义的数据结构与服务端返回的不一致。

DataBinding、Compose：维护 `数据层`、`视图层` 之间的联系，数据驱动UI。

业务代码：是 `数据层`、`视图层` 之间联系的纽带。

模块化的缺点：

* 编译时间长
* 模块间耦合严重
* 功能无法复用

### 小结
架构的核心是分层，

按业务分层可分为：`App壳` --> `业务组件` --> `功能组件` --> `基础组件`；
按代码结构分层为：`展示层` --> `逻辑层` --> `数据层`；

层与层之间如果不能直接引用则通过接口进行数据交互。

#### 命名后缀规则
- `Bean`：任何一个java类都可以成为一个bean，这个类里包含对象的属性、get、set方法及其他的业务逻辑。
- `Model`：model是MVC中的概念，可以理解为View层展示数据的对象。
- `Entity`：数据表对应到实体类的映射。
